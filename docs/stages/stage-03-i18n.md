# Этап 3. Локализация

Прочитай `CLAUDE.md` в корне репозитория. Все его правила действуют на этом этапе. При противоречии главнее `CLAUDE.md`.

## Контекст

Проект — каркас редактора, а не редактор под конкретный движок. Разработчик движка добавляет свои окна, меню, кнопки и тексты в папку интеграции `src/engine/`. Поэтому у локализации два вида потребителей:

- **каркас** — его собственные строки: вкладки, панели, раскладка, темы, общие кнопки;
- **интеграция** — строки конкретного движка, которые разработчик движка добавляет сам.

Оба используют один и тот же механизм, и для обоих работает проверка типов. Строки интеграции никогда не добавляются в словари каркаса: иначе каждое обновление каркаса будет конфликтовать с кодом движка.

## Цель

Своя система локализации без сторонних библиотек: два языка, английский и русский, переключение без перезагрузки, сохранение выбора, проверка ключей переводов компилятором как для каркаса, так и для интеграции. Страница документации на витрине.

Попутно: сторы больше не создаются при импорте модуля. Это касается нового стора языка и существующего стора темы.

## Порядок работы

Этап разбит на пять подшагов. Каждый подшаг — один логический модуль. Больше подшагов не добавляй. После каждого подшага остановись, перечисли все созданные и изменённые файлы, кратко опиши решения и жди подтверждения.

## Разрешённые зависимости

Новых пакетов нет. Множественные формы берутся из встроенного в браузер `Intl`.

## Требования

### Языки

- Языки: `en` и `ru`. Набор языков — константный массив, тип языка выводится из него.
- Язык по умолчанию — `en`. Язык браузера не учитывается.
- Выбор пользователя сохраняется между сессиями под ключом `editor-language`. Ошибки доступа к хранилищу не ломают приложение: работает язык по умолчанию.
- Атрибут `lang` на `<html>` всегда соответствует текущему языку.
- Язык переключается без перезагрузки страницы, все тексты интерфейса обновляются сразу.
- Добавление нового языка должно быть локальной правкой: добавить язык в массив, после чего компилятор сам укажет на все словари, где не хватает перевода.

### Словари

- В каждом словаре английский вариант — источник правды. Остальные языки обязаны содержать ровно те же ключи: лишний или недостающий ключ — ошибка компиляции.
- Ключ, которого нет в словаре, — ошибка компиляции при вызове перевода.
- Словари не хранятся одним большим файлом. Каждая функциональная часть описывает свои переводы рядом со своим кодом: часть каркаса — в своей папке, часть интеграции — в `src/engine/`.
- Проверка типов работает для словарей интеграции так же, как для словарей каркаса, без правки файлов каркаса.

### Подстановки и множественные формы

- Подстановка значений в текст: например, `Selected: {count}`.
- Множественные формы по правилам языка через `Intl.PluralRules`. Для русского обязательны формы `one`, `few`, `many`, `other` («1 объект», «2 объекта», «5 объектов», «1,5 объекта»), для английского `one` и `other`. Набор обязательных форм проверяется типами для каждого языка.
- Если подстановка ожидает параметр, а он не передан, это ошибка. Желательно на уровне типов; если это сильно усложняет код, допустима проверка в тестах. Предложи подход в подшаге 3.1.

### Использование

- В React-компонентах тексты получаются через хук, который перерисовывает компонент при смене языка.
- Реестры, сторы и любые данные вне компонентов хранят ссылки на переводы (ключи), а не готовые строки. Текст получается только при отрисовке. Иначе при смене языка часть интерфейса останется на старом языке. Это особенно важно для будущих реестров меню, тулбара и окон, куда интеграция будет добавлять свои пункты.

### Сторы без создания при импорте

Сейчас стор темы создаётся при импорте `src/state/theme/theme.ts` и сразу обращается к `window`. Из-за этого тест реестра витрины подменяет модуль через `vi.mock`, а на этапе UI-примитивов такие подмены распространились бы по тестам компонентов. В бэклоге это записано со сроком «до этапа UI-примитивов».

- Стор языка с самого начала не создаётся при импорте модуля.
- Стор темы переводится на тот же подход.
- После этого `vi.mock` для стора темы в тестах не нужен и удаляется. Пункт в бэклоге закрывается.
- Способ (ленивое создание при первом обращении, явная инициализация при старте приложения или другой) предложи в 3.1. Один способ для обоих сторов.

### Глоссарий каркаса

Термины каркаса переводятся единообразно. Базовый глоссарий:

| English | Русский |
|---|---|
| Window | Окно |
| Panel | Панель |
| Tab | Вкладка |
| Layout | Раскладка |
| Menu | Меню |
| Toolbar | Панель инструментов |
| Status bar | Строка состояния |
| Theme | Тема |
| Dark / Light / System | Тёмная / Светлая / Как в системе |
| Language | Язык |
| OK / Cancel / Apply / Close | ОК / Отмена / Применить / Закрыть |
| Reset | Сбросить |

Глоссарий хранится в `docs/glossary.md` и содержит только термины каркаса. Термины движков ведут разработчики движков у себя.

Правила русского перевода: обычный регистр предложения, а не каждое слово с большой буквы («Сбросить раскладку», а не «Сбросить Раскладку»); без точки в конце пунктов меню и подписей.

### Витрина

- Тексты документации на витрине остаются на английском и через систему локализации не идут.
- Переключатель языка появляется в шапке витрины рядом с переключателем темы: на витрине нужно видеть, как компоненты каркаса выглядят на обоих языках.
- Страница документации Localization по правилам раздела «Витрина» в `CLAUDE.md`.

## Подшаги

### 3.1. Проект системы, без кода

Пришли предложение и жди решения:

- API: как объявляется словарь функциональной части, как вызывается перевод, как выглядят подстановки и множественные формы.
- Как устроена проверка типов: совпадение ключей словарей, существование ключа при вызове, параметры подстановок, обязательные множественные формы для каждого языка.
- Как словарь интеграции получает ту же проверку типов, не правя файлы каркаса. Предпочтителен подход без глобального реестра всех ключей: например, перевод берётся из конкретного словаря, который передаётся явно. Если видишь подход лучше, обоснуй.
- Как хранится выбор языка. В `src/state/theme/` уже есть адаптер хранилища для темы. Оцени, стоит ли обобщить его для любых строковых настроек или сделать отдельный адаптер для языка. Обоснуй.
- Как сторы перестают создаваться при импорте: один способ для темы и языка.
- Как обеспечить, чтобы в коде не появлялись тексты интерфейса в обход системы. Например, правило ESLint, запрещающее текстовые узлы JSX вне `src/showcase/`. Оцени, что такое правило поймает, а что нет.
- Где в структуре папок живёт система локализации и где словари каркаса.
- Список файлов по подшагам 3.2–3.5.

### 3.2. Ядро

Языки, формат словаря, функция перевода, подстановки, множественные формы. Тесты, включая множественные формы для русского на числах 0, 1, 2, 5, 11, 12, 21, 22, 25, 101, 111, 1.5 и для английского на 0, 1, 2.

### 3.3. Состояние

- Хранение выбора языка, стор языка, синхронизация атрибута `lang` на `<html>`. Тесты по образцу темы: восстановление выбора, недоступное хранилище, мусорное значение.
- Перевод стора темы на создание не при импорте. Удаление `vi.mock` из тестов. Закрытие пункта в бэклоге.

### 3.4. Подключение к React и правила

- Хук для компонентов.
- Защита от текстов в обход системы, согласованная в 3.1.
- Словарь каркаса с терминами из глоссария.
- `docs/glossary.md` с глоссарием каркаса из этой инструкции.
- В `CLAUDE.md` новый раздел «Локализация» с правилами: все тексты интерфейса только через систему переводов; данные вне компонентов хранят ключи; строки интеграции не добавляются в словари каркаса; термины каркаса по глоссарию; правила русского перевода. Плюс выбранное место системы локализации в структуре папок.
- В `CLAUDE.md`, раздел React или «Состояние»: правило, что сторы не создаются при импорте модуля, и выбранный способ.

### 3.5. Витрина и итог

- Переключатель языка в шапке витрины.
- Страница Localization в разделе Foundations. Примеры, каждый отдельным файлом по правилам витрины:
  - объявление словаря и вызов перевода в компоненте;
  - подстановка значения;
  - множественные формы со счётчиком, который можно менять, чтобы увидеть формы на обоих языках;
  - словарь интеграции, объявленный отдельно от словарей каркаса, с той же проверкой типов.
- Итоговый отчёт этапа.

## Что не входит в этап

- Папка `src/engine/` и демонстрационная интеграция.
- Форматирование дат и чисел по языку.
- Языки, пишущиеся справа налево.
- Локализация текстов документации на витрине.

## Критерии приёмки

- Опечатка в ключе перевода, лишний или недостающий ключ в русском словаре, недостающая множественная форма — ошибки `pnpm typecheck`, и для словаря каркаса, и для словаря интеграции.
- Множественные формы русского языка верны на всём наборе чисел из 3.2.
- Язык переключается на витрине без перезагрузки, выбор сохраняется, атрибут `lang` следует за языком.
- Ни один стор не создаётся при импорте модуля, в тестах нет `vi.mock` для сторов.
- `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` проходят без ошибок и предупреждений.
